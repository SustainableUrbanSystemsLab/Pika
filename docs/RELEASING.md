# Releasing

Package: Yak, Rhino 8 for Mac only (the project targets `net8.0`, compiled against RhinoCommon 8.27, and references Rhino's Mac `System.Windows.Forms`). The GitHub Actions workflows mount the pinned Rhino 8.27 Mac installer for its .NET 8-compatible build tools. For a local build, set `RhinoDir` and `YAK` to the corresponding paths in a compatible Rhino installation if the installed app uses a newer runtime.

## Branches and channels

| Branch | Purpose | Yak version | Who can install it |
|---|---|---|---|
| `dev` | Day-to-day work; PRs target it. Never pushed to Yak. | none (local builds only) | nobody |
| `pre-release` | Beta candidates, merged from `dev` | `X.Y.Z-beta.N` | `yak install Pika X.Y.Z-beta.N`, or Package Manager with prereleases shown |
| `release` | Stable, merged from `pre-release` | `X.Y.Z` | everyone |

`<Version>` in `src/Pika/Pika.csproj` is the only place `X.Y.Z` lives; `scripts/build_yak.sh` passes it to Yak, overriding `yak/manifest.yml`. Semver: new feature → MINOR, fix → PATCH, breaking old `.gh` definitions (component GUID or parameter-order change) → MAJOR.

**A pushed Yak version is burned.** It can be yanked but never re-pushed, so build the exact file you tested.

## Before the first release (one-time)

1. The package name is `Pika` (`name:` in `yak/manifest.yml`), and it is permanent once pushed. `yak search` is a text search of Yak only, so also search food4rhino.com for it before the first push.
2. Choose a license and add `LICENSE` (README says none is selected yet).
3. Confirm `authors:` and `url:` in `yak/manifest.yml`.
4. Minimum Rhino is 8.27: the `RhinoCommon`/`Grasshopper` package versions in the csproj set the Yak tag (`rh8_27-mac`). `0.5.0-beta.1` was load-tested in Rhino 8.32 on .NET 8.0.14 (all 8 components construct); it has not been run in Rhino 8.27 itself.
5. `yak login` (opens a browser; needs a McNeel account).

## GitHub Actions

Modeled on Eddy3D's Yak workflows:

| Workflow | Trigger | Does |
|---|---|---|
| **Yak Release** (`yak-release.yml`) | push to `pre-release` or `release` | Builds, pushes to Yak, creates the GitHub release, checks Yak lists it. `pre-release` publishes `X.Y.Z-beta.N` with the next unused `N` (GitHub tags and Yak both checked); `release` publishes `X.Y.Z` and fails if it is already taken. |
| **Package Check** (`package-check.yml`) | PR into `pre-release` or `release` | Same build, no push; uploads the `.yak` artifact for testing. |
| **Yak Yank** (`yak-yank.yml`) | manual | Yank or unyank listed versions. |

All builds run `yak-package.yml`, which also fails if the package contains an assembly Rhino already supplies (RhinoCommon, Grasshopper, System.Windows.Forms, System.Drawing.Common, ...).

So a beta is: open a PR from `dev` into `pre-release`, test the Package Check artifact in Rhino, merge. A stable version: PR `pre-release` into `release`, merge. Bump `<Version>` on `dev` for the next series.

Publishing requires a `YAK_TOKEN_PATRICK` repository secret generated by an authorized package owner using [`yak login --ci`](https://developer.rhino3d.com/guides/yak/yak-cli-reference/#login). Keep the token in GitHub Actions secrets. If Yak accepts the upload but GitHub release creation fails, finish the tag and GitHub release from the run's `.yak` artifact. Yak versions cannot be uploaded twice.

## Manual beta (from `pre-release`)

Fetch the release branches and merge the latest development work into the beta channel:

```bash
git fetch origin
git switch pre-release
git merge --ff-only origin/pre-release
git merge origin/dev
```

For another candidate in the same series, increment the beta number. For a new series, update `<Version>` in `src/Pika/Pika.csproj` and start at `beta.1`. Check both GitHub tags and `yak search --all --prerelease Pika` before selecting a version. The `v1.0.0-beta.1` GitHub tag and its package already exist, so use `beta.2` for another `1.0.0` candidate.

Build and verify the package for the chosen version. For example:

```bash
suffix=beta.2
scripts/build_yak.sh "$suffix"
version="$(sed -n 's:.*<Version>\(.*\)</Version>.*:\1:p' src/Pika/Pika.csproj)-$suffix"
package="build/yak/pika-$version-rh8_27-mac.yak"
unzip -t "$package"
```

Test this exact `.yak` in Rhino. The geometry smoke check should produce **6 panels / 10.005996 m²** with the example model and current components. Some saved definitions need their ports reconnected after the component changes.

After testing, use `yak login` with a Pika package owner account and publish:

```bash
"${YAK:-/Applications/Rhino 8.app/Contents/Resources/bin/yak}" push "$package"
git tag -a "v$version" -m "Pika $version"
git push --atomic origin pre-release "refs/tags/v$version"
gh release create "v$version" "$package" --prerelease --verify-tag
```

## Stable (from `release`)

```bash
git switch release && git merge pre-release
scripts/build_yak.sh                 # X.Y.Z, no suffix
```

Repeat the example check, then `yak push` the file, `git tag vX.Y.Z`, push `release` and the tag, and create a GitHub release from the tag with the `.yak` attached. Merge `release` back to `dev` so the next cycle bumps `<Version>` from there.

## Yank

```bash
yak yank Pika X.Y.Z-beta.1
```

## Python in a Yak install

PV Weather uses a Python interpreter with `requirements-solar.txt` installed. From a source checkout, `scripts/setup_python.sh` creates that environment with `uv`. A Yak install can use it by setting `SOLAR_PYTHON` to the absolute path of `.venv/bin/python`. If Rhino starts from the Dock, use `launchctl setenv SOLAR_PYTHON <path>` and restart Rhino. The legacy PV Solar Conditions component additionally uses Ladybug Tools and Radiance `gendaymtx`.
